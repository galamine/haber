Engineering note · scheduling model

One game per session

How a session gets its game: the therapist picks it directly from the catalog at the moment they create the session — there is no plan-level game list in between.

Audience Clinic ops & engineering Touches session.ts, session-conflicts.ts, Prisma schema Status Implemented
In one sentence: a session is a discrete, manual act — the therapist picks its date, time, room, and exactly one game straight from the catalog when they create it; a plan is just the goals/metadata container the session is attached to, and never holds a game list of its own.
01

The three entities

A therapist builds a Plan for a child — goals, program length, that kind of metadata. Separately, whenever the therapist wants to schedule an appointment, they create a Session directly: date, time, duration, sensory room, and exactly one Game chosen from the shared Game/GameVersion catalog. There is no intermediate game pool on the plan — each session's game choice is made fresh, at session-creation time.

02

Why one game per session

The rule is a direct consequence of how creation works, not a separate constraint bolted on afterward: session.create takes a single gameVersionId as input, so a session can only ever be created with one game. A session can only ever record one result, and finishing that game fires a webhook that marks the session complete — there's no scenario where a session ends up with more than one game to reconcile.

This used to be enforced differently: an earlier, generation-first model let a therapist attach several games to a plan, then bulk-created sessions and round-robined the plan's games onto them. That generator is gone. What's left is simpler — the one-game-per-session guarantee is now just what the create form does, not a distribution algorithm working around a shared pool.

Completion still works

Every session has exactly one game, so the one‑result‑per‑session webhook logic needed no changes — it already assumed this.

No plan-level pool

Games come straight from the shared Game/GameVersion catalog per session; there is nothing on the plan to keep in sync.

Enforced in the database

A uniqueness rule on the session–game link (@@unique([sessionId])) makes it structurally impossible to reintroduce more than one game per session.

03

Edge cases

  • No game chosen. Not possible — gameVersionId is a required field on session.create, so a session can't exist without one.
  • Changing the game later. Not supported as a separate action; the session's single SessionGameAssignment is fixed at creation time, same as its date, room, and duration.

Duration check, now per session

The old plan editor warned when a game's runtime didn't fit the session's target duration, checked in aggregate across the plan's whole game pool (plan.checkSessionDuration). That procedure is gone along with the pool it inspected. The concern itself — does this game's length fit the session — is now simply implicit in what the therapist sees on the session-creation form: they pick the session's durationMinutes and the game's durationSeconds/repetitions in the same step, so there's no separate plan-level check left to run.

04

What didn't change

Everything downstream of "a session has one game" was already built around that assumption, so none of it needed to move:

  • The completion webhook still creates one GameResult per session and marks it complete on that call — that behavior is now simply always correct instead of only correct by accident.
  • The session detail screen and the plan's sessions list already render per‑assignment; with one assignment per session, they just show one card instead of several.
  • Nothing about how results are scored, stored, or displayed changed.
