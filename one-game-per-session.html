Engineering note · scheduling model

One game per session

How a treatment plan's games get scheduled onto sessions, why a session used to break when it held more than one game, and how round‑robin distribution fixes it.

Audience Clinic ops & engineering Touches session-generator.ts, plan.ts, Prisma schema Status Implemented
In one sentence: a plan can still hold several games, but each generated session now gets exactly one of them — assigned by cycling through the plan's game list in order, so game 1 goes to session 1, game 2 to session 2, and so on, wrapping back to game 1 once the list runs out.
01

The three entities

A therapist builds a Plan for a child and attaches one or more Games to it — that's the game library the plan draws from. The system then generates a run of Sessions (the actual scheduled appointments). Each session needs to know which single game to play.

02

The problem this replaces

Until now, session generation did the opposite of the diagram above: it took every game on the plan and attached it to every session — a full cross join. A plan with 3 games meant every single session carried all 3.

That collided with how completion actually works. A session can only ever record one result, and finishing any one game fires a webhook that marks the whole session complete immediately.

Net effect: playing game A ended the session before B and C were ever reachable in practice, and if a child did play them anyway, their results were silently dropped — not stored, not shown, not scored.
03

The fix: round‑robin distribution

Rather than reworking completion and results to handle several in-flight games per session, we removed the actual source of the conflict: a session generated for a plan now receives only one of the plan's games. Which one is decided by cycling through the plan's game list, in the order they were added, one game per session, wrapping back to the start once the list is exhausted.

The rule

session's game = plan.games[ session_index % number_of_games ]

Session 0 gets the plan's 1st game, session 1 gets the 2nd, and so on; once every game has had a turn, it starts over from the 1st. This keeps every game in rotation across the course of the plan instead of piling them all into every visit.

Completion still works

Every session has exactly one game, so the existing one‑result‑per‑session webhook logic needed no changes at all — it already assumed this.

Plans stay flexible

A plan can still hold as many games as a therapist wants; they just get spread across the plan's sessions instead of stacked into each one.

Enforced in the database

A uniqueness rule on the session–game link makes it structurally impossible for a future code change to reintroduce more than one game per session.

04

Worked example

A plan has 3 games (in this order: Balance Beam, Sound Match, Star Catcher) and runs for a course of 7 sessions. Here is exactly what each session is assigned:

05

Edge cases

  • No games on the plan. Sessions still generate on schedule; none get a game assignment until one is added — same as before.
  • Exactly one game. Every session gets that one game. Identical to what already happened for single‑game plans, so nothing changes for the common case.
  • Games that don't divide evenly (e.g. 3 games over 7 sessions, above). The remainder always falls to the games earlier in the list, since the cycle restarts from index 0 each time it wraps.

Duration check, adjusted to match

The plan editor warns when a game's runtime doesn't fit the session's target duration. That check used to sum every game's duration together — which made sense when every game played in the same session. Now that a session only ever plays one game, the check instead flags the plan's single longest game against the session length, since that is the one case that could actually overrun a visit.

06

What didn't change

Everything downstream of "a session has one game" was already built around that assumption, so none of it needed to move:

  • The completion webhook still creates one GameResult per session and marks it complete on that call — that behavior is now simply always correct instead of only correct by accident.
  • The session detail screen and the plan's sessions list already render per‑assignment; with one assignment per session, they just show one card instead of several.
  • Nothing about how results are scored, stored, or displayed changed.
