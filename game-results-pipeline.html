Reference · Game Results Pipeline

How a played game becomes a number on screen

Every therapy-session game — arcade catch/pop, tap-to-choose selection games, trail/draw sensory games — writes back one untyped JSON blob. This traces that blob from the webhook that creates it, through the code that guesses its shape, to the components that render it, to the (mostly separate) systems that actually drive clinical follow-up.

01

Storage

one JSON column, no per-game table

There is no table per game type. Whatever the game client sends after a play-through lands, verbatim, in a single Json column — the schema makes no attempt to know what shape a "ball-pop" result looks like versus a "trace-walk-alphabet" one.

packages/db/prisma/schema/sessions.prisma:57–68
model GameResult { id String @id @default(cuid()) sessionId String @unique sessionAssignmentId String? @unique rawMetrics Json @default("{}") recordedAt DateTime @default(now()) session TherapySession @relation(fields: [sessionId], references: [id]) assignment SessionGameAssignment? @relation(fields: [sessionAssignmentId], references: [id]) }
Written bywebhook, not tRPC
POST /api/sessions/:id/complete — a plain Hono route in apps/server/src/index.ts:99–142, authenticated by the session's own webhookSecret (not by user auth). Presumed caller: the game client itself, when a play-through ends. Idempotent — replaying with the same secret returns the already-stored result instead of erroring.
Body validationdeliberately loose
WebhookCompleteBody in packages/api/src/schemas/session-execution.ts: data: z.record(z.string(), z.unknown()). Any JSON object satisfies the contract — nothing enforces a per-game shape on write. Shape-awareness only exists on the read side (Stage 02).
1 session : 1 resulthard schema limit
Both sessionId and sessionAssignmentId are @unique. A session can only ever record one game result, even though it can have multiple SessionGameAssignment rows — see the matching workaround in Stage 02.

The game-registry isn't a result schema

packages/db/prisma/game-registry/*.ts (three files: catch-pop, selection, trail-draw-reveal) list playable builds — name, version, HTML entry path, level count, total time. It's consumed only by seed-games.ts to seed Game / GameVersion rows for the catalog UI. It says nothing about what a result payload looks like. GameVersion.scoringSchema (also Json) exists for that purpose but is never read by any parsing code — an unused field.

02

Parsing three shapes

shape-sniffed with Zod, not looked up by game id

packages/api/src/lib/game-result-summary.ts defines three Zod schemas — one per "family" of game — and tries them against rawMetrics in a fixed order. Whichever one parses first wins; the result carries a family tag from then on. There is no per-game-id table telling the parser which schema to use.

Arcade

Catch / pop games

ball-pop, apple-catch, balloon-pop, candy-pop
Game name nested under game.gameName. Flat stats block.
{ game: { gameName }, stats: { score, caught|popped, missed, accuracyPct, bestStreak, timePlayedSec } }
Selection

Choice / matching games

odd-one-out-*, yes_or_no_response_game
Game name nested under session.gameName. Per-round array + separate aggregate block.
{ session: { gameName }, rounds: [{ index, promptItem, result, decisionTimeMs }], aggregate: { correct, wrong, timeouts, accuracy, ... } }
Draw

Trail / draw / reveal games

reveal-animals, trace-walk-alphabet
gameName flat at the top level — no nesting at all. Progress milestones + optional embedded quiz.
{ gameName, timeTakenSec, stampCount, image|number, milestones: [{ pct, elapsedSec }], quiz?: { attempts, correct } }
packages/api/src/lib/game-result-summary.ts:178–189
// try each family's schema in order; first safeParse to succeed wins export function summarizeGameResult(rawMetrics: unknown): GameResultSummary { const arcade = ArcadeRawMetrics.safeParse(rawMetrics); if (arcade.success) return summarizeArcade(arcade.data); const selection = SelectionRawMetrics.safeParse(rawMetrics); if (selection.success) return summarizeSelection(selection.data); const draw = DrawRawMetrics.safeParse(rawMetrics); if (draw.success) return summarizeDraw(draw.data); return { family: "UNKNOWN" }; }
rawMetrics (Json)→ ArcadeRawMetrics.safeParse→ fail → SelectionRawMetrics.safeParse→ fail → DrawRawMetrics.safeParse→ fail → UNKNOWN

Normalizing field-name drift within a family

Even inside one family, raw field names vary by sub-game — the summarizers paper over it: hits: stats.caught ?? stats.popped ?? null (Arcade) and item: raw.image ?? raw.number ?? null (Draw). Whichever field a given game actually populated wins.

Matching the one result back to an assignment

matchResultToAssignments() reads the game's own name out of the already-parsed summary and compares it against each SessionGameAssignment.gameVersion.game.name. With today's one-assignment-per-session limit that's mostly redundant — but when there's exactly one assignment, an unrecognized (UNKNOWN) result still gets attached to it rather than being dropped.

03

What's shown

hardcoded per family, not config-driven

GameResultCard.tsx switches on resultSummary.family and renders one of three hand-written views. Nothing here reads GameVersion.scoringSchema or any other per-game config — labels, units, and rounding are all written directly into each component.

FamilyComponentWhat's shown
ARCADE ArcadeResultView.tsx In-game score · hits · missed · accuracy% · best streak · time played
SELECTION SelectionResultView.tsx Rounds · accuracy · correct/wrong/timeouts · avg/min/max decision time · attention pauses, plus a collapsible per-round table
DRAW DrawResultView.tsx Time taken · drawing coverage (stampCount) · item shown · a pacing sentence computed client-side from milestones · optional quiz badge
UNKNOWN (fallback text in GameResultCard) "Result recorded, but its format isn't recognized yet."

The pacing sentence isn't stored anywhere

DrawResultView walks the milestones array client-side to find the largest gap between percentage checkpoints and produces a sentence like "Paused longest before reaching 60% (12.3s)." That text is generated fresh on every render — it lives only in the component, never in the database.

game-library / platform/games — a different page entirely

These routes are catalog browsing and super-admin CRUD for Game / GameVersion metadata (name, category, age range, target issues, and a generic JSON viewer for scoringSchema). They don't render results — easy to conflate with the result views above by name alone.

04

Follow-up

read-only display — not fed back into planning

Game results are surfaced to therapists in a few places, and cross-session averages are computed for the printed progress report. But nothing in the codebase reads a past GameResult to choose a future game, calibrate difficulty, or drive a clinical decision — that entire loop is manual.

Where results surfacedisplay only
session.ts → attachResultSummary (session detail, plan sessions tab) and report.ts → childProgress feeding SessionSummary.tsx in the printable Progress Report.
Cross-game averagingwithin-family only
SessionSummary.tsx groups sessions by literal game name, then averages within a family — e.g. mean accuracy% for an Arcade game, mean decision time for a Selection game. There's no unified score spanning families; games that never parsed (UNKNOWN) are simply excluded.
Session "rotation"unrelated to results
session-generator.ts assigns games round-robin (assignments[index % assignments.length]) across a plan's generated sessions — fixed and structural, not informed by how a child performed on any prior game.
"Calibration"a different kind of calibration
The pf_calibration flag gating "Open Game" in the session detail page is a one-time webcam/pointer calibration step for the game iframe — not a clinical difficulty calibration, and unrelated to GameResult.
GameResult.rawMetrics→ summarizeGameResult→ session / report routers→ result views + progress report · no path back into plan or session generation

The real follow-up pipeline runs in parallel, not through this data

Clinical follow-up — goal attainment, sensory-profile deltas, plan revisions — is driven entirely by FollowUpAssessment / Goal / GoalProgressEntry, filled in by hand by a therapist via assessment.createFollowUp. None of it reads GameResult.rawMetrics. Dashboards (dashboard.ts) don't touch game results either — attendance % comes purely from TherapySession.status. The Progress Report is the only document that puts game-result data and therapist-entered clinical data side by side, and even there they're two independent sections, not one reconciled metric.

Known gaps

Unused scoringSchema
GameVersion.scoringSchema looks like it was meant to declare a per-game-version result shape, but no parsing or display code reads it — the three hardcoded family schemas do all the work instead.
One result per session
GameResult.sessionId and sessionAssignmentId are both @unique, so a session can hold at most one result — even though the schema otherwise models a session as having multiple SessionGameAssignments. matchResultToAssignments exists specifically to work around this.
Three families, not per-game validation
Any of the dozens of games in the registry maps into one of three broad shapes. A genuinely new metrics shape needs a new Zod schema, a new summarizer, and a new React view — three places to touch — or it silently falls into UNKNOWN.
No result-driven automation
Game selection, session rotation, and difficulty are all static/manual today. There's no code path where a past GameResult influences what happens next for that child.
