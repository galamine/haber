Reference · Treatment Plan Lifecycle

From draft to closed: every action on a treatment plan

A plan moves through four statuses — DRAFT, ACTIVE, PAUSED, CLOSED — but the interesting behavior lives in the actions that trigger, gate, or branch off those transitions. This maps every one of them, procedure by procedure, as they exist in plan.ts and goal.ts today.

01

Draft

status: DRAFT

The plan exists but nothing is running yet. It can be freely reshaped — activities and goals added, removed, reordered — before it ever reaches a family or a session calendar.

Createstarts the plan
plan.create — creates the record at versionNumber: 1, optionally seeded from a preset. UI: plans/new.
— → DRAFT
Manage activitiesbuild-out
plan.addGame · removeGame · updateGame · reorderGames — attach, remove, edit, or resequence assigned games/activities.
Add goalsbuild-out
goal.create — short-term or long-term goals, each starting at IN_PROGRESS.
Check durationvalidation
plan.checkSessionDuration — read-only check that assigned activity durations fit inside the configured session length.
02

Active ⇄ Paused

status: ACTIVE / PAUSED

Once activated, the plan is live: sessions exist, activities are being delivered, and progress is being tracked. It can be paused and resumed any number of times without losing history.

Activateenter live state
plan.activate — flips isActive: true and calls generateSessionsForPlan, which creates the TherapySession rows the plan will run on.
DRAFT / PAUSED→ACTIVE
Pausehold delivery
plan.pause — stops the plan without closing it out; nothing is deleted or finalized.
ACTIVE→PAUSED
Resumere-enter live state
plan.resume — the mirror of pause.
PAUSED→ACTIVE
Extendno status change
plan.extend — lengthens programLengthWeeks via a 4 / 6 / 8 / 12-week picker in the UI. Doesn't touch status.
Record progressno status change
goal.updateAttainment — logs a GoalProgressEntry against a FollowUpAssessment, updating each goal's attainment percentage over the life of the plan.
↻ Pause and resume can repeat indefinitely — this is the only two-way transition in the lifecycle.

Modify plan — the one action that forks, not flips

Unlike every other action here, plan.modify doesn't just change a status field. While the plan is ACTIVE, it:

  • Marks the current version isActive: false (its status field is untouched)
  • Creates a new plan row at versionNumber + 1, status: ACTIVE, linked back via parentPlanId
  • Copies over the activity assignments, then calls regenerateFutureSessions
  • Runs goal.applyPlanModificationDecisions for every existing goal — see below

Blocked entirely once the plan is CLOSED.

Per-goal decisions inside a Modify

continuecopied as-is
modifyold goal → DISCONTINUED+new goal → IN_PROGRESS(linked via supersededByGoalId)
discontinue→ DISCONTINUED
addbrand-new goal created on the new version
03

Closed

status: CLOSED — terminal

The plan is done. No further actions are exposed in the UI once a plan reaches this state — it's a dead end by design.

Closeend the plan
plan.close — sets closureReason and outcomeSummary, flips isActive: false.
any non-CLOSED→CLOSED

Known gap — worth a fix

The Close button in PlanLifecycleButtons.tsx currently submits closureReason and outcomeSummary as empty strings instead of prompting the clinician for them. The fields exist in the schema and are meant to capture why a plan ended — right now that context is silently lost every time a plan is closed.

Supporting lifecycles

Sessions (spawned by an active plan)

Each activation or modification generates TherapySession rows, which run their own independent state machine:

PENDING→IN_PROGRESS→COMPLETED
ABSENT(only from PENDING)
MANUALLY_CLOSED(from PENDING or IN_PROGRESS)

Who can act on a plan

Every mutation above resolves through the same guard before anything else runs:

  • Scoped to the caller's clinicId — never cross-tenant
  • THERAPIST / STAFF also need a ChildTherapistAssignment linking them to the child, or the call fails with FORBIDDEN
  • SUPER_ADMIN bypasses both checks
